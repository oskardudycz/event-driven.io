# Tailwind styling guidance

Reviewed 2026-10-11, with responsive hero/header research added on 2026-10-12 against the official sources below. These are repository rules for styling work. The rejected utility conversion has been reverted. The owner's subsequent request to continue authorizes the revised responsibility-based plan, starting with the shared shell.

## Goal and boundaries

Use Tailwind to make the layout easier to understand and change. Translating every CSS declaration into a utility, reducing stylesheet counts or moving an unreadable class string elsewhere does not satisfy that goal. Keep the existing Tailwind installation, theme switcher and useful component-owned styling.

Semantic HTML expresses meaning: article, nav, headings, lists, links and buttons. Utility names express presentation. Preserve both readable markup and accessible behavior; adding a class named article does not make a layout semantic.

Tailwind's documentation deliberately uses utility lists, including responsive and state variants. It does not promise short class attributes or prescribe a maximum class count. Our requirement is that the underlying design is simple enough to explain, with meaningful component boundaries and consistent values. A formatter cannot make a complicated layout simple.

## Shared-shell implementation

The first revised group keeps a stable header frame in normal document flow. Its bar can become fixed and shrink without moving content. The homepage frame alone overlays the hero. The visibility sensor follows the frame's bottom, replacing the inline height calculation. Articles retain their existing desktop reading gap of 50px; the former 90px header allowance and the archive's separate 80px allowance are removed. Reading widths and typography stay unchanged during this structural work.

Utilities use two named breakpoints: sm at 600px and lg at 1024px. Reset the default breakpoint namespace before defining these two, keeping a single unit system aligned with existing module rules and menu measurements. Mixing Tailwind's default rem thresholds with pixel-based header/menu rules would change their relative behavior when a visitor changes their browser's default font size. Remaining module media rules stay with their owners until their content-pattern group is simplified. The legacy emphasis token is --weight-emphasis, preserving its 600 weight without overriding Tailwind's standard font-bold (700). Pipeline tests check the standard bold/semibold weights, and browser checks cover the gallery threshold and header/content geometry.

These choices remove page/header coupling and repeated literal variants. They are foundations for the content-pattern work, not a claim that replacing CSS Modules with utility lists is itself an improvement.

## Responsive hero and header research

Reviewed 2026-10-12 after reproducing the reader's crop on production at 1280×1000. The agreed behavior is: retain a meaningfully visible face/upper body wherever the photo can sit beside readable copy; use tiles alone where the photo would interfere. A tall window is not, by itself, a reason to hide the photo. Keep one coherent tile pattern. Restore an independently dark homepage header and reduce its oversized presentation.

### Observed causes and rejected experiments

`src/images/png/hero-background.png` is a 3840×2160 flattened composition containing the tiles, yellow shape, speaker and a dark strip along its top. The current hero uses that artwork as a covering background; its height also follows viewport height and content. CSS `cover` preserves the image's ratio and crops the excess. With left alignment, the speaker on the right can fall outside the visible area. This is standard [background-size behavior](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/background-size), rather than a Gatsby extraction or hydration defect.

The following attempts were rejected and are not accepted fixes:

- Hiding the photo based on a guessed viewport aspect ratio: this removed it from a desktop layout where it could remain visible.
- Combining a contained full composition with a second covering tile crop: the differently scaled tile patterns produced visible seams.
- Shifting the flattened background while narrowing headings to percentages: the 1280×1000 capture still put white body copy over the yellow shape. Moving the face into view did not establish readable copy.
- Leaving the homepage header transparent: its apparent contrast depended on the artwork's baked-in dark strip, which moves when the background crop changes.

Unaccepted hero positioning/crop experiments and the unfinished screenshot test were removed. No visual reference was updated. The production defect remains open; earlier shared-shell acceptance does not certify this follow-up.

### Supported implementation direction

Use real layout areas for the copy and photo. [Tailwind's responsive guidance](https://tailwindcss.com/docs/responsive-design) demonstrates mobile-first stacked/side-by-side layouts; its [grid utilities](https://tailwindcss.com/docs/grid-template-columns) define columns and gaps directly. Prefer a small set such as `grid items-center gap-8 lg:grid-cols-2` on the actual container, with ordinary semantic children. This is an illustrative structure, not a final breakpoint or an instruction to force equal columns if the content does not fit.

Make the background texture independent of the photo before implementing that structure. Both Paint.NET sources were inspected; `assets/hero-background-right.pdn` contains separate tile, yellow-shape and speaker layers matching the deployed artwork. Native-resolution exports and reproduction details are recorded in [hero-exports.md](../assets/hero-exports.md). The original sources and flattened PNG remain intact. Do not simulate transparency with another opaque rectangle or invent a replacement portrait.

Gatsby [documents StaticImage for a fixed index-page hero and GatsbyImage for prop-driven images](https://www.gatsbyjs.com/docs/reference/built-in-components/gatsby-plugin-image/). Use the existing plugin rather than adding a background-image package. Give the photo its own intrinsic dimensions and use `objectFit="contain"` where the complete subject must remain visible. Gatsby defaults to `cover`, so this choice must be explicit. Use [documented art direction](https://www.gatsbyjs.com/docs/reference/built-in-components/gatsby-plugin-image/#withartdirection) or native [picture/source selection](https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Responsive_images) only when actual alternate image compositions are required.

Keep painted copy and controls outside the visible photo and yellow shape; transparent image canvas is not painted artwork. Let content determine the hero's height. Choose the photo visibility breakpoint from both languages' measured fit, including enlarged text, rather than guessing from a single screenshot. [Container queries](https://tailwindcss.com/docs/responsive-design#container-queries) are available if the component must respond to its parent's width; they are optional, not an automatic addition. Do not introduce ResizeObserver-based crop calculations.

The shared header must own its surface, spacing and portrait alignment. Its dark homepage surface must work with any hero image and in SSR. The implementation uses the ordinary 80px header frame and 44px avatar on the homepage; the hero's near-black color also supplies the header surface, independent of image pixels. Preserve the existing themed sticky state and mobile navigation. Browser geometry, responsive captures and visual review must verify this change.

The first implementation's centered 1280px equal-column composition was rejected. Production measurements at 1910×930 show the concrete regression: the H1 shifted from x=40 to x=315, its width fell from 1464px to 620px, and it grew from two lines to four. The cropped texture changed the image ratio and therefore enlarged the tiles. Geometry tests passed but did not establish a good design. Do not treat non-overlap as visual acceptance.

The owner authorized a justified responsive redesign, but rejected the subsequent 3:2 grid because the constrained image shrank instead of moving. Do not use a percentage column as a substitute for preserving the artwork's scale. Use the original transparent export at its half-resolution display size (772×722), keeping its aspect ratio and authored pixels. Native [CSS Grid layering](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Grid_layout/Basic_concepts#layering_items_with_z-index) supports items sharing an area; intrinsic sizing keeps the artwork within the hero even in a short window. Transparent space can share the wider heading's layout area, but actual text and control paint must remain outside the artwork. Validate this against the image's alpha channel and both languages, not just non-overlapping rectangular columns.

The prose uses Tailwind’s standard `max-w-xl` (36rem), independently of the wider heading. Measured at 1280×1000 in both languages, 38–42rem still overlaps the artwork with the SSR fallback font; 36rem clears both fallback and Open Sans text without changing the photo scale. Copy starts at the composition’s top, rather than being vertically centered beside the diagonal shape. [GOV.UK layout guidance](https://design-system.service.gov.uk/styles/layout/) informs readable prose length, not an article-width cap on the whole hero. Use a component size query with a font-relative fit threshold if measurements show that enlarged browser fonts need more room. This concerns artwork fit only; shared header/menu breakpoints remain aligned at 1024px. Do not add JavaScript crop calculations or guessed aspect-ratio hiding.

Keep the uninterrupted tile canvas at its original 3840×2160 ratio, with one background. Preserve Open Sans, wording, training/consulting actions, header geometry and the original person/yellow shape. Visibility must follow measured readable fit. The previous version's local verification is historical evidence, not acceptance of this correction.

### Navigation disclosure

The reported overflow panel used a translucent surface, fixed top offsets and unlabeled icon links. Use an opaque surface and visible names in the panel, retaining compact icons in the header with accessible names. Anchor the panel to its navigation container, bound its height by the viewport and give links full-width targets. Follow [W3C disclosure navigation](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/): ordinary navigation links, a button with expanded/controls state, Tab navigation and Escape returning focus to the button. Close when focus or a pointer moves outside the navigation. Do not introduce ARIA menu roles without their application-style keyboard behavior. Preserve locale destinations and mobile navigation.

The first open-panel capture exposed the hero copy above the navigation: its unnecessary positioned `z-index: 1` layer intercepted real clicks. Playwright’s native `click({ trial: true })` reproduced that failure. Remove the copy’s positioned layer; ordinary grid paint order already handles the transparent artwork. Do not raise unrelated z-index values to compete with it. Test every visible panel link for actionability as well as its text, color and bounds. The expanded homepage trigger also uses the same opaque dark surface, with state derived from its `aria-expanded` attribute.

Validate compact CSS viewports and enlarged text separately. [W3C's Reflow guidance](https://www.w3.org/WAI/WCAG21/Understanding/reflow) explains why content should wrap within narrow CSS viewports, including those produced by zoom. A small viewport test is evidence for reflow; it is not a claim that native browser zoom or all WCAG requirements were tested. No new visual references are accepted until the revised composition has been reviewed.

The revised build exposed a Polish fallback-font defect at 320px before Open Sans loaded: the long uppercase heading expanded its flex item and made the document 356px wide. Use Tailwind's documented [overflow wrapping](https://tailwindcss.com/docs/overflow-wrap) on the copy container. `wrap-anywhere` lets intrinsic flex sizing account for emergency word breaks; normal word boundaries remain preferred. Do not clip the overflow or shrink the entire page to conceal it. Test both languages with web-font requests blocked as well as with JavaScript enabled/disabled.

### Tailwind and CSS ownership

Use standard utilities for grid/flex, gap, alignment, sizing and visibility where they make the source simpler. Use existing theme roles and named breakpoints. Keep the tile background/artwork styling, complex sticky transitions and typography rules in their owning CSS Modules when clearer. Tailwind [explicitly supports custom CSS](https://tailwindcss.com/docs/adding-custom-styles); keeping a focused module is idiomatic. Neither a utility-only rewrite nor a new component framework is required. Keep Gatsby image/data plumbing outside portable layout markup for a future Astro migration.

### Acceptance before calling this fixed

Review EN/PL captures at 320/390px mobile, 768×1024 tablet, 1024px desktop boundaries, 1280×1000 (the reproduced defect), 1440×900 and 1920×1080; include short windows, 200% zoom and enlarged browser fonts. Check the face and upper body, copy/photo separation, one coherent tile pattern, header contrast/height and avatar containment. Check initial HTML, hydration, scrolling, sticky return, both themes and language navigation.

Use native Playwright assertions for element containment/non-overlap and screenshot comparisons for the actual composition. When inspecting Gatsby images, evaluate the exact selected image node rather than finding another image by its src: main and noscript images can share that URL. Reuse the loaded-image assertion before synchronous canvas inspection. The Firefox JavaScript-disabled diagnostic stalled when awaiting decode on the other image; the corrected helper passes all eight affected EN/PL desktop cases. Review intentional new layout references explicitly; preserve existing tolerances and do not add missing references automatically. Run build, project tests, lint/format and browser checks sequentially. Keep diagnostic screenshots under ignored `visual-artifacts/`, not as accepted fixtures. Record local, hosted and production evidence separately.

Wait for the destination heading after Gatsby client navigation before measuring it; a changed URL does not establish that its new content is rendered. Use [Playwright's web-first assertions](https://playwright.dev/docs/test-assertions) rather than sleeps or a non-null assertion on an immediate bounding box. For cross-browser typography checks, compare exact browser-resolved CSS values: the Firefox diagnostic reports `17.5938px` for both the existing article type and an isolated literal `17.6px` declaration, while Chromium reports `17.6px` for both. A plain CSS reference preserves the intended size and exact comparison without widening tolerances or changing application styles.

## Rules for implementation

1. Describe the layout responsibility and the rules being eliminated before editing. If the result has the same exceptions in a different syntax, reconsider the design.
2. Use standard utilities and a consistent spacing/type/width scale. Keep meaningful surface, text, accent and border roles backed by the shared light/dark CSS variables. Do not create a token for every historical number or calculation.
3. Use named responsive variants. Arbitrary values are a documented feature, suitable for justified exceptions; repeated literal breakpoints and header-compensation formulas signal an unresolved design problem.
4. Use semantic elements and existing React components. Extract a component when it owns useful behavior, meaningful markup or a repeated pattern. Avoid a new wrapper for every class list or a generic variant framework for hypothetical reuse.
5. Keep small utility lists beside the elements they style. Do not move a large list into a constant, invent an alias or use @apply merely to make the JSX appear shorter. Loops and actual shared components can remove genuine duplication.
6. Keep authored prose, syntax highlighting, reading-order counters and intricate animation in their owning CSS where that remains clearer. Tailwind adoption does not require deleting every CSS Module.
7. Preserve CSS ownership: shared reset/fonts/theme in the layout, component styles with their owner. No extraction-order imports, specificity escalation, !important rescue rules or duplicated global selectors.
8. Review SSR and hydrated output. Preserve locale navigation, focus, keyboard controls, reduced motion, theme persistence, provider behavior and existing content. Keep Gatsby data/routing adapters separate from portable presentation.

For example, an article container should need to express centering, reading width and gutters. It should not know the header's height or reproduce its positioning rules. A shared card should own cover, heading and metadata markup because these form a repeated content pattern, rather than exist solely to conceal utility classes.

## Execution groups and acceptance

Start with the shell and design scale together. Inspect article, archive, homepage, category, search and 404 layouts to find all header compensation. Compare proposed desktop/mobile arrangements, including the homepage overlay, before expanding the conversion. The owner accepts a close, well-designed result; preserve typography and interactions, and explicitly review intentional geometry changes.

Next, migrate shared content patterns together: reading/search cards, metadata/author information and article navigation. Use consistent layouts and states across their consumers. Preserve reading order, localized destinations, covers, sharing features and accessible labels.

Finish with straightforward controls/media and remove rules made redundant by the new structure. Leave complex scoped styling where it remains clearer. Measure generated output before claiming a performance improvement.

Before accepting each group:

- Explain which layout exceptions, duplicated decisions or DOM wrappers were removed, and show the resulting source for readability review.
- Run types, lint/format, smoke checks, production build and the full test suite. Run relevant browser tests in EN/PL, light/dark, mobile/desktop, plus keyboard, reduced motion, scrolling and client navigation.
- Keep screenshot tolerances unchanged. Review intentional differences and update fixtures only for an explicitly accepted change; never regenerate snapshots to make a failing conversion pass.
- Test CSS/utility edit and restoration on warm builds when stylesheet ownership or utility generation changes. Check SSR/hydration for consistent appearance.
- Before hydrated screenshots, use expectFonts from tests/browser/readiness.ts. Browser font readiness can resolve while Arial is still active, before React requests and activates Open Sans; waiting for document.fonts.ready alone does not establish the final typography. This was observed in Firefox's font registry and computed styles. Run project/browser suites sequentially as CI does when validating readiness deadlines.
- Interface controls inherit the page's font family from the shared base layer. Native buttons and fields otherwise use browser-specific defaults even when body text uses Open Sans. Preserve component-owned font sizes/weights and the existing loading-failure fallback; do not enable all of Preflight just to normalize fonts. The owner explicitly requested consistent Open Sans on 2026-10-11.
- Record actual local results, remaining warnings and separate hosted/deployed evidence in todo.md.

Keep visual references specific to the browser/platform they certify. The initial two Firefox homepage failures also occur on the unchanged Git build; before the authorized Open Sans correction, the shared-shell refactor produces zero homepage pixel differences. The owner authorized current production as the baseline on 2026-10-11. Manually reviewed production Firefox captures now have their own project-name path, with existing Chromium files and the 3% limit unchanged. All 53 selected Firefox header/theme/font cases and four loading-failure cases pass. Evidence and the reference decision are in [the visual review](header-visual-review.md). Do not alter layout or typography to make different rendering engines produce identical pixels.

Official Tailwind class sorting can standardize ordering later. Evaluate its compatibility with the existing Pongo-aligned Prettier/ESLint setup before adding it. Sorting is formatting support, not an architecture check. Do not add arbitrary class-count limits or migration-reversion tests.

## Sources and interpretation

- [Tailwind: styling with utility classes](https://tailwindcss.com/docs/styling-with-utility-classes) documents design constraints, arbitrary values and managing duplication with loops/components. The repository's readability requirement is our acceptance criterion, not a claim that Tailwind prohibits long class lists.
- [Tailwind: responsive design](https://tailwindcss.com/docs/responsive-design) documents mobile-first named variants, resetting the default breakpoint namespace and using consistent units. This site's two pixel-based named thresholds keep existing CSS and menu behavior aligned, including browser font preferences.
- [Tailwind: theme variables](https://tailwindcss.com/docs/theme) explains the namespaces that generate utilities. The font-weight collision above is observed in this site's tokens and failed conversion.
- [Tailwind: Preflight](https://tailwindcss.com/docs/preflight) documents its border reset and how to omit it. This site intentionally omits it; future work must account for that.
- [Gatsby: layout components](https://www.gatsbyjs.com/docs/how-to/routing/layout-components/) describes React composition and persistent shared layouts. It supports putting shared shell responsibilities together, without prescribing this site's visual design.
- [Gatsby: CSS Modules](https://www.gatsbyjs.com/docs/how-to/styling/css-modules/) documents scoped, portable component styling. Keeping appropriate modules is a supported choice alongside utilities.
- [MDN: FontFaceSet.ready](https://developer.mozilla.org/en-US/docs/Web/API/FontFaceSet/ready) describes readiness for current font loads/layout. Waiting for the application's computed font family as well is based on the observed React activation timing above.
- [MDN: styling form fonts](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Styling_web_forms#fonts_and_text) documents that native controls may not inherit their parent's font and recommends explicit inheritance. This is the supported shared reset mechanism used for consistent Open Sans, rather than per-component font overrides.
- [Playwright: visual comparisons](https://playwright.dev/docs/test-snapshots) explains why browsers/platforms require separate reference images. This site's shared reference path predated the broader Firefox run; the optional project-name template now separates its reviewed production references from default Chromium images.
