### Ordering warnings are not yet a demonstrated cascade defect

The fresh build succeeds in 159.30s and repeats nine extraction-order warnings and four slow category-query warnings. Installed versions are Gatsby 5.16.1, css-loader 5.2.7 and mini-css-extract-plugin 1.6.2. Use their actual behavior, not the newest Webpack/plugin examples, as the compatibility baseline.

At the original baseline, all nine CSS warnings paired List.module.css with layout-owned styles; CategoryTemplate and PostTemplate request opposite traversal orders. Installed Gatsby's browser export includes PageRenderer, whose dependencies include the plugin layout hook; List's Link and Post Author's withPrefix reach that path at different points. This is a source-level explanation, not captured chunk-graph proof or evidence that a user-visible rule wins incorrectly. List uses local classes; reset rules have low specificity; layout/header/footer selectors largely target other elements. This needs an emitted-selector audit before classifying the warnings as harmless or actionable.

The [installed extraction plugin's documentation](https://github.com/webpack/mini-css-extract-plugin/blob/v1.6.2/README.md#remove-order-warnings) permits ignoreOrder only when scoping/naming has mitigated ordering. Repository guidance forbids suppressing these diagnostics; do not enable it. Reordering an import solely to obtain a quiet build is not an accepted architecture change. Keep normal ownership and demonstrate the conflicting cascade/dependency first. An old Gatsby 2 issue reporting success with reordered imports is not sufficient proof for this Gatsby 5 setup.

### Removed cache workaround

`scripts/css-module-ident.mts` formerly read all source CSS for each local class and made every class depend on every stylesheet. Its exposed loader callback did not make that algorithm Gatsby's recommended caching mechanism. It coupled unrelated components, repeated filesystem work and changed unrelated class exports on every style edit. It is now deleted after the isolated platform correction passed; the observable stale-inline-CSS regression is retained and extended to global CSS.

The research did not identify a documented production switch or released upstream fix. The version-pinned dependency correction and its maintenance conditions are recorded in the completion section above. Gatsby's installed ForceCssHMRForEdgeCases is a development HMR mechanism; it is not a supported application fix for production HTML caching. Do not copy or monkey patch that implementation.

## Reproduced causes and correction boundaries — 2026-10-08

This investigation compared documentation, the installed Gatsby 5.16.1 implementation, a two-page reproduction outside this repository, and the actual built site. Documentation alone did not establish a defect.

### Persistent layout and multilingual navigation

[Gatsby's layout guide](https://www.gatsbyjs.com/docs/how-to/routing/layout-components/) and [wrapPageElement API](https://www.gatsbyjs.com/docs/reference/config-files/gatsby-browser/#wrapPageElement) support a persistent layout. The [translation plugin](https://www.gatsbyjs.com/plugins/gatsby-plugin-react-i18next/) supports that layout plugin, localized Links, per-page GraphQL resources and language-specific URLs. Our provider structure and locale-prefixed routes are supported; replacing them is not required to fix menu styles.

The actual defect is in Menu's data/state ownership. Its constructor retains the initial page models. `overflow.mjs` then copies translated anchor text into `hiddenItems`, discarding translation keys and icons. Since Gatsby preserves Layout during client navigation, this copied English text survives the switch to Polish. On the built site at 1280px, the main menu becomes `Wystąpienia`, while the opened overflow menu still says `Talks`; its social entries contain no icons. At 390px, switching language after opening leaves both `showItem` and `hideItem` on the same elements. Their current computed display is hidden, but the contradictory DOM state is real.

The supported correction follows [React's state structure guidance](https://react.dev/learn/choosing-the-state-structure) and [DOM ref guidance](https://react.dev/learn/manipulating-the-dom-with-refs): derive item models from current props, retain only overflow indexes and the open flag, read widths through refs after rendering, and let JSX own visibility classes. Render overflow entries from the same current models, so translation keys and icons survive. Keep existing breakpoints, spacing, colors and interactions. Class component lifecycle methods remain supported; converting every component or replacing the translation provider would not address this cause.

### Extraction diagnostics versus the emitted cascade

Gatsby merges extracted styles into one stylesheet in `webpack.config.js`. The installed MiniCssExtractPlugin computes desired module order from each chunk group's dependency traversal; it does not analyze selector overlap. Category and post templates reach List and the persistent layout in opposite traversal orders. The Gatsby browser barrel reaches PageRenderer, the browser API runner and layout wrapper, creating a dependency cycle through otherwise normal Gatsby imports.

The isolated two-page fixture reproduces the warning with component-owned CSS and layout-owned globals. Replacing gatsby-plugin-layout with documented browser/SSR wrapPageElement hooks produces the same warning. Therefore removing that supported plugin solely to silence the warning is not justified. Direct imports from gatsby-link would bypass the framework graph but its own README explicitly says not to import that package directly.

On the built site, a PostCSS-preserving browser audit moved the reading-list rules before and after the remaining stylesheet. All computed properties, including before/after pseudo-elements, stayed identical across eight combinations: English/Polish, 390/1280px, Event Sourcing category/Open Source article. This demonstrates order independence for those exercised surfaces; it does not certify every hover, focus or dormant component. Keep the diagnostics visible and extend coverage where a concrete cascade defect appears. No import manifest, reordered unrelated dependencies, ignoreOrder, CSS chunk override or new cascade layers are proposed as a fix.

### Production CSS-only cache failure

The isolated official-PostCSS fixture uses normal path/local-name class identifiers and layout-owned global styles. A warm build changing `.list` from `rgb(1,2,3)` to `rgb(9,8,7)` emits `styles.8c5f882355bc38cadea6.css` with `#090807`, while both page HTML files still inline `styles.418f4f47c63cc9d23f23.css` with `#010203`. Restoration succeeds. This is stale HTML, not an ignored CSS transform or a browser/CDN cache problem.

Installed-source trace: Gatsby enables its Slice build machinery in `bootstrap/load-config/index.js`, even without application Slice components. `redux/reducers/html.js` skips browser-compilation-hash invalidation on that path. `commands/build.js` and `utils/webpack/get-ssr-chunk-hashes.js` instead track server renderer/template chunks. CSS declaration changes with unchanged class exports leave those renderer hashes unchanged, so affected HTML is reused despite the new extracted asset. [Gatsby's build overview](https://www.gatsbyjs.com/docs/conceptual/overview-of-the-gatsby-build-process/) describes selective HTML rebuilding; the reproduction exposes a missing dependency at that boundary.

Control experiments strengthen that trace: the same failure occurs without the PostCSS plugin, using Gatsby's built-in CSS handling. That isolated Node 24 test needed the legacy OpenSSL provider because the installed default class-name hash uses MD4; the flag was not added to this project. In a second diagnostic-only fixture control, restoring browser-hash HTML invalidation makes the declaration-only edit regenerate both pages with the correct current CSS. That control changes a private environment variable after Gatsby initializes it, so it is evidence about the cause, not a supported production remedy.

The former all-source class hash compensated for this gap by changing renderer exports. That broad workaround is now deleted; the version-pinned dependency correction tracks CSS assets at the actual HTML reuse boundary. Do not introduce an undocumented Slice environment override, private Redux actions, post-build HTML replacement, or another global invalidator. A proper platform correction must track the current CSS asset when deciding whether cached HTML is reusable, with an upstream fix/release or an explicitly reviewed dependency patch. No confirmed supported production switch or released correction has been identified in this review. The publisher's registry reports stable/latest as 5.16.1 and next as 5.17.0-next.1 on 2026-10-08; upgrading to another stable release is therefore not an available correction today.

Temporary reproduction logs are in /tmp/css-repro-\*.log; built-site cascade and locale evidence are /tmp/css-cascade-audit.log and /tmp/css-navigation-audit.log. These are local investigation artifacts, not publication content, checked-in migration assertions or CI/deployment acceptance.

## Custom code that is justified

- Native `useStaticQuery`, Gatsby Image, Gatsby Head, explicit schema types and supported Gatsby hooks are appropriate platform usage. They do not require replacement for modernization alone.
- The translation plugin plus editorial PageContext handle distinct concerns: translation resources/navigation versus canonical language, placeholder availability and reading-order policy. Overlap in manual onCreatePage decoration should be audited, but the explicit bilingual policy is intentional.
- MiniSearch uses a real library, lazy index loading and a build hook for static indexes. Locale fallback, covers and safe React text highlighting are site requirements, not reasons to add a different search plugin.
- The YouTube adapter delegates rendering to gatsby-remark-embed-video and preserves timestamps/referrer behavior with existing tests. Keep it until the upstream plugin supports the required behavior and a comparison proves the adapter can be removed.
- The image-priority adapter promotes one measured Introduction cover while keeping later/unrelated images lazy. It is narrowly scoped, but hard-coded source/image names should eventually become explicit editorial data rather than grow into more special cases.
- Imported Markdown HTML, article notes and JSON-LD need supported HTML/script rendering paths. Their presence is not itself a vulnerability. Retain escaping, URL validation and hostile-input regressions; do not label all dangerouslySetInnerHTML calls unsafe without checking their data source.
- The approved newsletter IntersectionObserver has cleanup and an automatic/no-JS fallback. Keep the approved interaction; Disqus remains unchanged.
- Cache verification deliberately edits/restores source fixtures in an opt-in integration harness. That is test tooling, not publication content. Keep restoration checks and avoid concurrent builds while it runs.

## Proposed consistent module policy — not implemented

Target first-party code uses ES module import/export, `.ts` without JSX and `.tsx` with JSX. Browser/server JSX hooks, pages and components target `.tsx`. Native ESM Gatsby config/node boundaries must be settled against the documented `.mjs` loader and TS-to-CommonJS limitation above; do not promise `.ts` native ESM hooks or force them with a runtime shim. Choose documented boundary exceptions as part of the coordinated policy, not ad hoc file-by-file renames.

This requires a dependency-wide plan, not filename changes alone:

1. Map package boundaries, local plugins, Node scripts, React code, tool configs, tests, CI commands and all import paths. Account for content/meta config, currently CommonJS under a package boundary.
2. Establish TypeScript configurations and a real type-check gate. Use Gatsby API/PageProps/HeadProps types and declarations for CSS/YAML imports. Keep Gatsby-bundled JSX distinct from Node-executed scripts.
3. Adopt explicit package ESM and native Node 24 TypeScript for erasable script syntax, with explicit file extensions and type-only imports. Node does not execute TSX or type-check code; an ESM-aware test transform is required for React tests. See [Node 24 TypeScript documentation](https://nodejs.org/docs/latest-v24.x/api/typescript.html).
4. Verify each tool's actual loader before choosing its config filename. [ESLint documents TypeScript config loading](https://eslint.org/docs/latest/use/configure/configuration-files#typescript-configuration-files); [PostCSS's loader documents TS peers](https://github.com/postcss/postcss-load-config/blob/main/README.md). Installed versions must be checked; do not introduce undocumented runtime shims.
5. Execute coherent categories after review: platform/config/shared modules; scripts/import/local plugins and their tests; React pages/components and TSX tests. Update imports, commands, lint-staged, editor settings, cache keys, CI and documentation in the same category. No component-by-component arbitrary stopping points.
6. Require installation, type-check, lint, smoke, build, full tests, browser/visual and warm-cache checks. Renamed source changes component chunk identities, so a cold platform build and compatible cache-key update are required. Retain content URLs/contracts and screenshot tolerances.

Any genuine tool-loader limitation must be recorded with a supported alternative before implementation. A file-extension consistency goal does not justify changing runtime behavior or adding compilation workarounds.
