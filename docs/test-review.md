## Research and decisions

- [Playwright best practices](https://playwright.dev/docs/best-practices): observable behavior, isolated tests and third-party requests, retrying assertions and controlled visual data. Keep native fixtures/assertions and the current runner.
- [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots): environment/fonts matter; focused element comparisons are supported. Keep 3% tolerance, explicit review and separate Firefox references. Do not mask content or rewrite the DOM to pass comparisons.
- [Testing Library principles](https://testing-library.com/docs/guiding-principles/): exercise what users see and do. Geometry selectors can identify measured regions; historical prose and unrelated implementation assertions are not behavioral contracts.
- [Gatsby GraphQL component testing](https://www.gatsbyjs.com/docs/how-to/testing/testing-components-with-graphql/): supply representative query data at framework boundaries. Use synthetic article fixtures for routing, not old import manifests and bodies.
- [Astro rendering tests](https://github.com/withastro/astro/blob/main/packages/astro/test/content-collections-render.test.ts) build dedicated fixtures and inspect generated HTML/CSS. [VitePress E2E tests](https://github.com/vuejs/vitepress/tree/main/__tests__/e2e) use a controlled documentation site, including local-search fixtures. Exact text/counts are appropriate for controlled fixtures, not a growing production archive.
- [AstroPaper scripts](https://github.com/satnaing/astro-paper/blob/main/package.json) provide build/type/lint/format checks, but no comparable application regression suite. Fewer scripts are not evidence that this site's locale/security/responsive checks are unnecessary.

Separate current-content completeness from stable representative visual coverage. New posts need no screenshot update. Editorial wording is now independent of pixel references; intentional styling changes still need review.

[Vitest projects](https://vitest.dev/guide/projects) support multiple named configurations in one process and filtering with `--project`. Use current `projects`, not deprecated `workspace`. [Vitest fixtures](https://vitest.dev/guide/test-context) provide scoped setup/cleanup and `onTestFinished`; use these instead of porting Node's `context.after` through an adapter. Keep the existing static-rendering assertions where SSR output is the contract.

[Vitest's React renderer](https://vitest.dev/api/browser/react) supplies asynchronous rendering, locator-compatible queries, automatic cleanup and rerender support. Its documentation identifies it as a community package; it is documented by Vitest, not part of React or Playwright. [React Testing Library](https://testing-library.com/docs/react-testing-library/intro/) is a rendering/query helper rather than a runner. Both encourage role/label queries; neither replaces real-site SSR and navigation tests. Before installing a renderer/provider, check its actual published peer ranges against the installed Vitest/React/Playwright versions.

These packages were inspected, not installed, during this repair. Recheck registry metadata when implementing the migration.

[Vitest screenshot testing](https://vitest.dev/guide/browser/visual-regression-testing) supports native component comparisons and recommends distinct visual projects. Preserve reviewed images and tolerances when evaluating migration; verify screenshot naming, viewport, CSS Module exports, fonts and theme initialization first. Separate visual assertions from behavior so editorial changes remain independent of references. Do not approve new images merely because a runner changed.

### Full-site migration boundary

[Vitest explicitly says Browser Mode does not replace standalone E2E runners](https://vitest.dev/guide/browser/why). Its [Playwright provider](https://vitest.dev/config/browser/playwright) shares a page across tests in a file, unlike Playwright Test's per-test isolation. Its [custom command context](https://vitest.dev/api/browser/commands) exposes an orchestrator page hosting the test iframe, which should not be navigated away from. Changing existing `page.goto` tests to Browser Mode is therefore not an import replacement.

Vitest Node tests can launch the Playwright library through fixtures, but preserving our production suite would then require owning context options, trace attachments, server lifecycle and screenshot comparison/reporting. That is a bespoke E2E harness, with more maintenance than the existing supported runner. Do not launch Playwright Test's CLI from a Vitest test to label it migrated. The owner accepted the boundary on 2026-10-13: logic/generated-output/component tests use Vitest; real-site E2E retains Playwright Test under the same grouped npm test workflow.

### Astro comparison and agreed integration

Rechecked official documentation and repository examples on 2026-10-13. [Astro's application testing guide](https://docs.astro.build/en/guides/testing/) documents Vitest configuration through `getViteConfig()`, component rendering through its Container API and separate Playwright E2E against built/preview output. React browser tests use the Vitest Playwright provider; Astro-specific rendering would use Astro's documented compiler/container boundary, with built-site tests still proving actual hydration/assets. Detailed configuration, isolation, helpers, CI ordering, screenshot migration and framework boundaries are in [the testing guide](testing-guidance.md#using-vitest-and-playwright-together), linked from AGENTS.md. This follow-up changes guidance and settled scope; runner migration remains pending.

### Useful helpers, structure and commands

Use native [Playwright fixtures](https://playwright.dev/docs/test-fixtures) for browser resources and cleanup, keeping the existing context-level external traffic policy. Use role/label locators, web-first DOM assertions and [expect.poll](https://playwright.dev/docs/test-assertions#expectpoll) for measured geometry. Introduce a small feature helper only for repeated behavior, with explicit inputs; avoid generic action dispatchers, classes and custom polling frameworks.

Proposed structure: `tests/unit/<feature>/`, `tests/generated/<feature>/`, `tests/components/<feature>/`, `tests/e2e/<feature>/`, plus shared fixtures/helpers. Separate mixed pure/build assertions before moving files. Public commands should cover `test`, `test:unit`, `test:generated`, `test:components`, `test:e2e`, watch/review and explicitly reviewed reference updates. Filter by feature/path/project through runner arguments instead of a script per file. Keep specialized cache mutation probes separate from ordinary tests. Update CI, README and VS Code together; remove obsolete aliases and alphabetize script groups.

### Development feedback

Yes: [Gatsby Fast Refresh](https://www.gatsbyjs.com/docs/reference/local-development/fast-refresh/) updates components/styles while developing. Use [Playwright's webServer](https://playwright.dev/docs/test-webserver) to start/reuse the development server and run a small client-behavior group covering locale navigation, search and theme/menu controls. Reuse cases/tags where behavior is mode-independent. Keep development startup/rerun timings separate from component test timings; Gatsby still initializes its content graph.

Development mode does not establish production SSR/no-JavaScript behavior, extracted CSS, optimized assets, canonicals, sitemaps or feeds. Retain those checks against a production build before publication. Development and production generation share `.cache`/`public`; do not start both while validating the same output. The existing component gallery provides the cheapest no-Gatsby-build CSS feedback while the runner refactor is pending.
