# Keeping LLM-assisted design consistent

Researched 2026-10-14. Scope: tools and approaches for keeping this blog's colours, typography, images and components coherent across AI-assisted changes. This is a research comparison, not an installation, product benchmark or approved redesign. Official documentation establishes capabilities; first-party case studies establish reported experience, not independent proof of universal results.

Current process: [DESIGN.md](../DESIGN.md) consolidates the recommendation below with Figma import, lean Storybook and Astro considerations. Earlier phased recommendations here are research context; use that entry for ongoing work.

## Main finding

The useful pattern is **shared design decisions + real implementation examples + rendered feedback**. A longer aesthetic prompt alone does not provide reliable component APIs, asset identity, theme pairings or responsive behaviour. Skills, Markdown files, CLIs and MCP servers are different ways to deliver that context. None replaces source ownership or review.

For this repository, retain CSS tokens, component-owned styles and existing checks. The revised process recommends a lean Storybook catalogue reusing the current gallery data, with MCP as a follow-up and optional Figma exploration. DESIGN.md is now the discoverable process entry; hosted platforms remain separate workflow choices.

## How others approach it

**Atlassian provides a concrete engineering case study.** Its design-system team moved component usage, props, tokens, accessibility and other guidance into typed schemas alongside code, generating agent-facing formats from that source. This addresses stale or contradictory context and invented APIs. Their reported improvements come from internal tasks; they do not establish an equivalent gain for this small blog. [Teaching AI to speak our design language](https://www.atlassian.com/blog/ai-at-work/teaching-ai-to-speak-our-design-language)

Atlassian subsequently delivered the same content through a skill, MCP server and CLI. Its September 2026 account reports comparable quality with a tuned CLI, about 8% less task time and 8% fewer tokens than its MCP baseline. The useful lesson here is to evaluate retrieval against real tasks and inspect agent behaviour, rather than treating MCP as inherently superior to local files or terminal tools. [CLI case study](https://www.atlassian.com/blog/ai-at-work/giving-ai-agents-design-system-context-from-the-terminal-what-we-learned-building-a-cli)

**Google's Stitch work emphasises portable design intent.** Its open-source draft DESIGN.md specification describes carrying design rules between tools/projects, including why colours are used. It is useful context, not an enforcement engine or a guarantee that arbitrary agents automatically discover the file. A repository instruction should explicitly direct the agent to it. [Google announcement](https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-design-md/)

**Figma emphasises mapping design to real code.** Code Connect supplies imports, usage snippets, property mappings and custom instructions through Figma MCP. This is more actionable than reconstructing everything from screenshots. Mappings and the design library still need maintenance. [Code Connect integration](https://developers.figma.com/docs/figma-mcp-server/code-connect-integration/)

**Storybook emphasises component retrieval and feedback.** Its MCP can expose documentation, examples and test tools so agents use existing components and validate work. The current documentation labels the AI features preview; component documentation requires enabling a supported components manifest. React is supported. This is a documented capability, not a tool tested in this repository. [Storybook MCP](https://storybook.js.org/docs/ai/mcp/overview)

## Images need a related but different workflow

UI consistency comes largely from reusing components and tokens. Image generation remains variable. Maintain a small set of approved references, dimensions/crops, subjects, palette relationships and examples of acceptable output. Record the generator/model and settings when generating a repeatable series; do not rely on a seed alone as a durable visual specification.

[Adobe Firefly style references](https://helpx.adobe.com/ca/firefly/web/work-with-images/generate-images/reference-images-for-styling.html) and [structure references](https://developer.adobe.com/firefly-services/docs/firefly-api/guides/concepts/structure-image-reference/) provide controls for visual style and composition. [Midjourney Style Reference](https://docs.midjourney.com/hc/en-us/articles/32180011136653-Style-Reference) transfers aesthetic characteristics; it explicitly distinguishes this from copying the depicted people or objects. These tools guide similarity, not exact brand compliance. Neither was used or evaluated here.

For this blog, retain the real speaker portrait and authentic workshop photographs. If generating future editorial illustrations, use approved examples and review the result. Keep factual diagrams and EventStorming labels in editable diagram/vector source. Render logos, exact text, colours and layout through deterministic templates where appropriate. A reusable SVG template is sufficient for simple social cards; [Satori](https://github.com/vercel/satori) is an optional HTML/CSS-to-SVG renderer if JSX-driven templates become useful. An LLM can draft the subject or copy while the template fixes type, spacing and branding.

An asset inventory should distinguish active, legacy, proposed and approved artwork. This matters here: a source favicon and the checked-in HB icons disagree. An agent should report that conflict, not automatically designate whichever file it finds first as the brand master. Source code describes current implementation; it is not automatic approval of every inherited asset.

Use [DESIGN.md](../DESIGN.md): a single process linking actual tokens/components/assets, a lean catalogue, optional Figma exploration, reviewed changes and existing validation. ## A proportionate experiment

### Repository-specific effort and value

Follow-up assessment, 2026-10-14: the existing gallery is adequate for controlled visual checks, but Storybook is a reasonable addition now if the objective includes repeated LLM-assisted UI work. The source already separates portable author/archive/reading/search views from Gatsby adapters and runs them with React/Vite, real CSS Modules, global tokens and self-hosted fonts. That makes a small catalogue substantially easier than introducing one into a framework-coupled application.

The current `editorial.story.tsx` exports ordinary React scenarios, not Storybook CSF metadata. Those scenarios/data can be reused, but merely displaying the combined page would provide weak per-component discovery. Useful adoption needs typed stories with component metadata for the actual views, alongside a combined editorial example. Retain component-owned styling and the existing CSS Module naming convention, static asset serving, font readiness and locale/theme setup.

| Scope                                                                         | Rough engineering effort          | Result                                                                                                                                                        |
| ----------------------------------------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| React/Vite setup and initial catalogue from existing views                    | About half a day to one day       | Component navigation, individual previews, theme/locale controls, viewport selection and basic docs.                                                          |
| A useful initial set with prose/control/image states and accessibility review | About one to two days total       | Representative examples for branding work, with required wrappers and actual styles/assets.                                                                   |
| MCP discovery and validation                                                  | Additional half day if compatible | Verify the component manifest exposes real props/examples, then test actual agent retrieval. Test-running tools may need additional Vitest-addon integration. |

These are estimates from source inspection, not measured delivery times or a completed install spike. Peer compatibility with the installed React 19, Vite 8 and Vitest 5 must be verified before installing; current npm metadata could not be retrieved through the research browser. The official MCP documentation identifies AI features as preview. Integration failures could increase the estimate.

Immediate value is a standard browsing/documentation/controls interface instead of growing a custom preview toolbar. MCP adds queryable component knowledge once real stories and their manifest are present. Neither provides brand decisions automatically. Ongoing work includes adding representative states when APIs change and maintaining Storybook/addon dependencies; the separate handwritten guide is still needed for intent and approved assets.

Recommended initial scope: use Storybook as the component catalogue, reuse existing controlled examples/data, retain current Vitest screenshot coverage and Playwright Gatsby coverage, and retire the manual gallery launcher only after parity is demonstrated. Do not maintain two separate preview catalogues long term. Add the accessibility panel, then a verified MCP integration. Treat the Vitest addon/test migration and hosted publication as separate choices, preserving accepted references and tolerances. No dependency changes, test migration or installation was performed for this assessment.

If choosing between the existing gallery and Storybook, use a small pilot with the same tasks and model: one article/card change, one search/control-state change and one transparent-image example. Compare component reuse, invented props/tokens, unrequested styling, review corrections and total effort. Keep real hero/Gatsby validation independent. A working preview is necessary but not enough: verify the component/source choices as well.

The revised recommendation is **a lean Storybook catalogue reusing existing examples/checks**, with MCP after useful component discovery is established. The current gallery remains in use until parity is verified. Figma/Penpot/Pencil are worth investigating if you want an editable design workspace; v0/Builder/Supernova fit broader generation or team workflows. No subscription, account connection, package installation, agent skill, MCP server or production change was made for this research. Prices, account-specific permissions and exact package compatibility would need checking before adoption.
