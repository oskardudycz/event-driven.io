# Gatsby and modern Tailwind blog comparison

Research date: 2026-10-10. Project baseline: `5a2554226afe491fda20509b6f5f34da6b3961ed`. This is a source, configuration, registry and dependency-resolution review, not a starter build benchmark. Sample sources and raw evidence are downloaded under `/tmp/gatsby-starter-research-2026-10-10/`; nothing from a starter was installed into this application.

## Findings and current status

1. The official minimal Gatsby starter needs just Gatsby, React and React DOM. It still resolves a large compiler/development dependency graph and reproduces upstream peer warnings and audit findings. Removing our unused declarations cannot remove packages Gatsby itself requires.
2. The official Gatsby blog is the useful same-framework baseline: Markdown, images, feeds, Head metadata and explicit GraphQL types with 17 direct declarations. Our additional bilingual routing, search, importers, indexing, deployment tooling and regression checks explain much of the difference; some unnecessary code and declarations remain.
3. **AstroPaper is the primary modern Tailwind reference.** It is popular, recently maintained, uses Tailwind 4, native modules and typed content, and is directly relevant to the possible later Astro migration. The popular Tailwind Next.js Starter Blog supplies a second, richer React reference. Its architecture is modern, but its pinned Next/React/tool versions are not today's latest: copy individual patterns after verification, not its manifest.
4. Our direct upgrades passed earlier application checks; that does **not** mean the dependency cleanup, peer compatibility or security work is complete. Several overrides compensate for unsupported peer ranges; vulnerable nested packages remain despite current root versions. The previous acceptance wording overstated the result.
5. The owner has now authorized retiring the inactive form. Its component, CSS, barrel, unused translation keys and Ant Design dependency are removed. The live EN/PL contact pages still offer Calendly. The subsequent portable-foundation implementation is recorded below. A replacement form, theme redesign, search replacement and framework migration are not implemented by this review.

## 2. What was inspected and measured

- Read complete manifests, lockfiles, framework configuration, layout/metadata/font/theme/search/content code and lint/format settings in the selected samples.
- Read this project's source, Gatsby/PostCSS/ESLint configuration, package commands, local plugins, tests, deployment and install hooks. Use TypeScript AST import extraction plus configuration/CLI review; an absent source import alone does not make a Gatsby plugin or CLI unused.
- Check npm registry `latest`, engines and peer ranges. The existing dependency review lists every direct version; registry JSON snapshots are kept in temp. Aliases are resolved to their targets rather than treating a missing registry package under the alias name as an error.
- Resolve copied manifests in separate temp directories with Linux Node **24.12.0**, npm **11.9.0**, `npm install --package-lock-only --ignore-scripts`. Original sample lockfiles remain untouched in their checkouts. These probes use **fresh range resolution**, not `npm ci` against the samples' original locks.
- Audit the generated locks and record warnings. No sample lifecycle scripts or builds run. Therefore the findings establish dependency-resolution behavior, not successful starter builds, equivalent features, browser payload sizes or PageSpeed scores.

An initial shell resolved a Windows npm executable. Those outputs were preserved with `initial-windows-npm-` names and excluded from results. All reported probes were rerun with the explicit Linux Node/npm paths. Audit classifications can change between requests; the table uses the saved `audit.json` snapshots, not the earlier install-summary output.

## 3. Differences worth adopting

### Gatsby-native content and metadata

The official blog already uses GatsbyImage, Gatsby Head and explicit GraphQL field types. This repository already adopted those mechanisms; restoring Helmet, gatsby-image, typography plugins or a separate CSS Modules integration would regress the stack. Its createPages query requests IDs/slugs rather than article HTML/images, resolving content in page queries. Compare our remaining resolvers with that separation only where profiling demonstrates a cost. See the pinned [official Gatsby node hooks](https://github.com/gatsbyjs/gatsby-starter-blog/blob/d75052245100ae3c98807c5f38c6e7ec68910e74/gatsby-node.js).

The minimal and official blog omit direct Babel packages: Gatsby owns its compiler. Our direct Babel/Bluebird/core-js declarations are already removed. They remain transitively because Gatsby and some plugins use them; deleting nested packages would break their ownership contract. The official blog's CommonJS hooks and older React/Prettier ranges are not a reason to undo our TypeScript/ESM work.

Gatsby documents [CSS Modules](https://www.gatsbyjs.com/docs/how-to/styling/css-modules/) and matching browser/SSR [wrapPageElement](https://www.gatsbyjs.com/docs/reference/config-files/gatsby-browser/#wrapPageElement) hooks. A future removal of gatsby-plugin-layout can use those hooks, but must preserve persistent layout state and verify SSR/navigation/font readiness. It is a small plugin reduction, not a fix for Gatsby's compiler graph. Keep each module with its component.

### Portable styling and themes

AstroPaper's [global stylesheet](https://github.com/satnaing/astro-paper/tree/35cfa7fbe0b897306d27670d3819e55d5205f3dd/src/styles) separates semantic CSS variables from Tailwind utilities. Its theme attribute and ordinary CSS work across frameworks. The Next blog's [Tailwind stylesheet](https://github.com/timlrx/tailwind-nextjs-starter-blog/blob/b45bef66b40c63b6f57c15ee8cd090682238df4c/css/tailwind.css) similarly uses CSS-first Tailwind 4 configuration, explicit source scanning and a dark variant.

For Gatsby, use `tailwindcss` + **`@tailwindcss/postcss`** through the existing gatsby-plugin-postcss/PostCSS pipeline. Do not copy Astro's `@tailwindcss/vite`: Gatsby's site bundler is webpack; this repo's Vite is test tooling. Tailwind 4 handles its own imports/prefixing, but that does not establish that our remaining CSS Modules no longer need postcss-nested or preset-env. Inventory their actual features before removing either. Sources: [Tailwind PostCSS installation](https://tailwindcss.com/docs/installation/using-postcss), [upgrade guide](https://tailwindcss.com/docs/upgrade-guide).

Approved approach: keep useful component-owned modules, add Tailwind utilities for actual layout improvements, and use CSS as the single editable token source. Do not mechanically convert every module declaration. There is no need for a second styling framework, CSS-in-JS runtime or a dark-mode Gatsby plugin.

Do not enable Preflight, the typography plugin or a new dark palette by copying the templates: they change resets, article styles and appearance. Tailwind 4 targets Safari 16.4+, Chrome 111+ and Firefox 128+; the owner has accepted modern CSS output for this baseline. Dark mode also needs an early theme choice without a flash, persistent explicit preference, keyboard/screen-reader controls, contrast checks, reduced-motion behavior and SSR-safe handling of storage/OS preference. Source: [Preflight](https://tailwindcss.com/docs/preflight), [dark mode](https://tailwindcss.com/docs/dark-mode), [compatibility](https://tailwindcss.com/docs/compatibility).

### Content, search and highlighting

AstroPaper validates content with a typed collection schema. Gatsby schema customization and generated GraphQL types serve the corresponding purpose here; strengthen content boundaries and use Gatsby's [GraphQL type generation](https://www.gatsbyjs.com/docs/how-to/local-development/graphql-typegen/) before considering a separate CMS/content compiler.

The Next starter adds Contentlayer2, MDX, Pliny, many remark/rehype transforms and math/citation support. These are real features, not simplifications for our Markdown blog. Do not add MDX/Contentlayer/Pliny to reduce package count. Preserve portable Markdown and the existing importer sanitization, alt descriptions, video rules, source identities and locale-aware link mapping.

AstroPaper uses Pagefind against built output; this avoids a custom content-index generator but still needs locale scoping, excerpts, lazy loading, covers and result UX. Its default UI disables result images; our search deliberately includes covers. Its development workflow also needs a built index. Pagefind is a credible future alternative, **not an immediate upgrade over working MiniSearch**. The Next starter's kbar/Algolia integrations also add packages we already retired or do not need. Source: [Pagefind multilingual indexing](https://pagefind.app/docs/multilingual/).

Astro uses build-time Shiki highlighting; Next uses rehype-prism-plus. Our existing Prism transform already runs at build time. Switching highlighters is not automatically a performance improvement; compare languages, resulting HTML/CSS, bundle inclusion and accessibility before changing it.

### Fonts, layout and UI dependencies

The official blog uses Fontsource; AstroPaper uses Astro's build-time font integration; Next uses next/font. None justifies changing our approved self-hosted Open Sans or reintroducing a remote font request. A native CSS Font Loading API can replace fontfaceobserver while preserving per-weight readiness and unmount handling. Measure fallback/CLS separately: loading fewer runtime packages does not prove a visible font change is safe. Source: [CSS Font Loading API](https://developer.mozilla.org/en-US/docs/Web/API/CSS_Font_Loading_API).

The unused ThemeContext and runtime YAML copy are removed in the foundation, with CSS tokens now directly editable; ScreenWidthContext and FontLoadedContext are actively used and must remain until their owning behavior is redesigned. These are concrete cleanup candidates, not a reason to rewrite every class component.

The custom AsyncComponent is used for share controls. React.lazy/Suspense may simplify it, but loading/error boundaries and SSR need a measured comparison. Keep active react-share controls/counts until the owner approves a native share-link/Web Share alternative. React icons are actively used; inspect actual bundle output before replacing them with static SVGs.

## 7. Future contact form: research, not implementation

The official Gatsby minimal/blog and AstroPaper do not provide a contact-delivery implementation to copy. The rich Next blog demonstrates a newsletter API route via Pliny, not a verified contact-form delivery pipeline. Do not transplant its server/API dependency into this static site.

For basic name/email/message fields, start with semantic HTML controls, labels, browser validation and owned CSS Modules; no Ant Design or form-state library is needed. Gatsby's [forms guidance](https://www.gatsbyjs.com/docs/how-to/adding-common-features/adding-forms/) distinguishes the frontend from processing/delivery. On the current host, [Netlify's documented static HTML form handling](https://docs.netlify.com/manage/forms/setup/) is the first implementation to evaluate: detection must be enabled, named fields/form must exist in generated HTML, then hosted capture and notifications must be verified. A client-rendered form needs its documented registration/form-name mechanism. Add AJAX only as progressive enhancement with visible pending/error/success states; preserve a working native submission path.

The old inactive form could never register through a page because it was not rendered. It also declared a honeypot name without providing that field. These source observations do not establish why older historical hosted submissions failed: account detection, spam filtering and notification delivery were not verified. A future acceptance check must submit on a preview, verify the dashboard record and actual notification delivery, then repeat for both locales, keyboard flow, invalid inputs, spam handling and network failure. Netlify documents [spam filters/honeypots](https://docs.netlify.com/manage/forms/spam-filters/); compare account quotas/cost before calling a hosted form free. No backend/provider is selected here.

## 8. Proposed execution order

1. **Complete this research and retire the authorized form.** Store evidence/decisions; validate deletion and retain current contact behavior.
2. **Remove demonstrated unused code/declarations as a group.** pngjs, inert resolver settings and unused theme provider; assess Playwright declaration duplication. Preserve observable tests instead of adding tests that pin the migration/package list.
3. **Resolve project-owned compatibility and security debt.** Isolated ESLint replacement/equivalent accessibility checks, localization peer reproduction, committed-vs-fresh lock placement; same-range audited fixes, then owner-scoped upstream experiments. Record supported, locally verified exception and blocked states separately.
4. **Simplify fonts/layout/head using native supported APIs.** FontFaceObserver replacement, metadata ownership and optional lazy/layout wrappers, with measured payload/CLS and navigation regressions. Do not combine this with a typography redesign.
5. **Approved CSS foundation category.** Decide Tailwind/browser floor/token source; introduce its supported PostCSS integration with existing modules and resets preserved. Then design light/dark palettes and components as separate reviewed visual categories.
6. **Optional Astro proof of concept later.** Use portable Markdown, tokens, components/data boundaries and existing route/feed/sitemap/search/import contracts. Do not run a second production framework or port the site as part of dependency cleanup.

Each implementation category needs a fresh install, lint/types, relevant behavioral/security tests, production output comparison and proportional browser checks. Any lock/React/layout/font/routing change needs the existing full build/browser/cache acceptance. Do not regenerate screenshots automatically. Hosted CI and deployment remain separate checks.

### What the type packages mean

An `@types/...` package describes another package's API to TypeScript. Type-only imports and ambient declarations are erased when producing browser JavaScript; that does **not** mean the described library is unused. `lodash/kebabCase.js` creates category URLs in site/node.ts, src/utils/category-posts.ts, src/pages/category.tsx and src/components/Post/Meta.tsx. Turndown is called by import/import-substack.ts to convert fetched HTML into Markdown, with its GFM plugin preserving tables and other Markdown features. The importer runs in Node; its dependencies do not need to be shipped to readers. Types are retained for these active APIs.

### Sharing alternatives

react-share is active and maintained; age alone does not justify removing it. Our controls use Twitter, Facebook and LinkedIn sharing plus Facebook counts. Native provider intent URLs can replace the buttons without a sharing package, but popup behavior and counts change. The Web Share API offers the device's share sheet where supported and requires a user gesture and HTTPS; ordinary links should remain as a fallback. A copy-link action is another provider-independent option. Keep current features for now; measure delivered code and the count request, then review whether those features are worth retaining. A different React button package would not inherently be simpler. Sources: [react-share](https://github.com/nygardk/react-share), [Web Share API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Share_API).
