---
description: "Tests should describe what your system does, not how it's built. Articles on writing tests that read that way, plus practical setup for .NET, Node.js and Java."
---

Two threads run through these articles. One is about tests that describe behaviour: why behaviour-driven design is more than test syntax, why mocks often check implementation details, and a small library that makes tests read as given, when, then. The other is practical setup: running the same tests against several configurations, starting real dependencies in containers, and checking that message formats stay compatible. For testing event-sourced code, see the [Testing](/en/guides/testing/) guide.
